# 技术教训档案

每个重大 bug 的现象 / 根因 / 修复 / 预防，按发现顺序归档。版本号对应 CHANGELOG.md。

---

## 1. Android 15 强制 edge-to-edge，内容顶到状态栏底下（v0.2.1）

- **现象**：真机（Android 15）上「今日」标题与系统时间/图标重叠。
- **根因**：targetSdk 35 后系统强制 edge-to-edge，WebView 从状态栏下开始绘制；且 WebView 内 `env(safe-area-inset-*)` 恒为 0，CSS 安全区方案失效。
- **修复**：原生读取 WindowInsets 换算 dp，注入 CSS 变量 `--safe-top / --safe-bottom`，页面与弹层统一避让。
- **教训**：不要假设浏览器标准（env() 安全区）在 WebView 里可用——WebView 是被 App 嵌装的环境，安全区必须由原生层显式提供给 Web。

## 2. 状态栏图标"隐身"（v0.2.2）

- **现象**：顶栏避让修好后，时间/信号/电量几乎看不见。
- **根因**：edge-to-edge 下系统默认画白色状态栏图标，而应用顶栏是浅色底。
- **修复**：主题声明 `windowLightStatusBar`（浅色底→深色图标），夜间资源反向声明。
- **教训**：处理状态栏时，"位置"和"图标明暗"是两个独立问题，要分开验证。

## 3. PWA Service Worker 在 APK 里缓存陈旧（v0.4.1）

- **现象**：底部页签除今日外全部点不动；新功能资源是旧的。
- **根因**：APK 内注册的 PWA SW 用旧缓存响应请求——路由懒加载的 chunk 拿不到，新功能资源陈旧。
- **修复**：APK 内彻底禁用 SW 注册并清理历史注册（资源随 APK 分发，本不需要 SW）；网页端 PWA 行为不变。
- **教训**：SW 是"网络缓存层"，只对网络分发的场景有意义；打包分发的壳环境里它只会制造陈旧数据。

## 4. 路由懒加载 chunk 在 WebView 不可靠（v0.4.1）

- **现象**：与 3 同源——懒加载的页面 chunk 加载失败。
- **修复**：路由改回静态导入；体积优化改由组件内按需动态 import（echarts），失败只影响局部。
- **教训**：WebView 里动态 import 依赖资源加载路径，可靠性弱于静态打包；性能优化优先做"组件级按需"，不做"路由级拆包"。

## 5. 调试签名不一致，两种来源的 APK 互相装不上（v0.3.1）

- **现象**：本地 apk.bat 打的包升级后，GitHub Releases 下载的包安装被拒（反之亦然）。
- **根因**：本地与 CI 各自随机生成 debug 密钥。
- **修复**：固定 debug.keystore 提交进仓库，gradle 显式指定。
- **教训**：任何"两条产线出同一个产物"的场景，签名/版本/配置必须同源。

## 6. vitest 把 Playwright 的 spec 当自己的测试（v0.7.0 CI 失败）

- **现象**：CI 单测 job 失败：`Playwright Test did not expect test.describe() to be called here`。本地未复现。
- **根因**：vitest 默认 include 匹配所有 `*.spec.js`，把新建的 `e2e/app.spec.js` 也加载了。
- **修复**：vitest `test.include` 显式限定 `tests/**/*.test.js`。
- **教训**：同一仓库引入第二套测试框架时，第一套的文件匹配规则必须收窄；"本地没复现"往往是因为新目录是本地最后一次运行之后才建的。

## 7. GitHub Actions 的 branches+tags 触发器陷阱（v0.3.0 Release 未发布）

- **现象**：打了 v* 标签，Release 步骤没执行。
- **根因**：`on.push` 同时定义 branches 和 tags 时，只有一次推送同时命中两者才触发；且合并推送只产生一次运行、ref 取分支——发布步骤的 ref 条件永远为假。
- **修复**：push 触发器不过滤 ref，任务级 `if` 按 ref 分流。
- **教训**：CI 触发器的过滤条件组合语义要看官方文档逐字确认，不能凭直觉。

## 8. 打卡面板异步重置竞态，目标关联丢失（v0.7.4）

- **现象**：编辑器里关联了目标，目标详情却是 0 关联。
- **根因**：面板打开时 `watch(show)` 里先 `await` 加载历史数据、再重置表单——快速选择目标会被随后的重置清空。时序竞态导致问题"时有时无"。
- **修复**：表单重置同步执行，异步只补充数据源、不触碰表单。
- **教训**：弹窗/页面的"初始化"与"数据加载"必须分离；凡是 await 之后重置状态，都要假设用户已经在这段时间里输入了内容。

## 9. GBK 批处理的两层编码坑（v0.5.0 前后多次）

- **现象**：bat 脚本中文乱码、行被截断、命令静默失效。
- **根因**：三层——① cmd 按 ANSI(GBK) 逐行解码，UTF-8 中文错位；② 已存在的 GBK 文件被现代编辑器按 UTF-8 有损读写（中文变 `?`）；③ GBK 中文某些字第二字节恰为 `0x5C`（反斜杠），吞掉行尾换行导致下一行命令被吞。
- **修复**：写 UTF-8 → PowerShell 转 GBK+CRLF；改 GBK 文件用 Node latin1 字节级补丁；管道/计划任务类逻辑脚本内容用纯 ASCII。
- **教训**：Windows 批处理是编码雷区——逻辑脚本宁可牺牲注释可读性也要 ASCII 化。

## 10. 全新安装无默认分类（v0.7.0）

- **现象**：未连服务器的全新环境无法开始打卡（无分类可选）。
- **根因**：默认分类只由服务端播种，客户端从未播种——一直被"连接过服务器"的测试路径掩盖。
- **修复**：客户端首启播种与服务器同 id 的默认分类（连接后 LWW 一致化）。
- **教训**：只测"开发者的环境"会漏掉"全新用户的第一分钟"；E2E 用全新浏览器上下文正是为了暴露这类问题。

## 11. 调度循环里"停第一条"停错了事件（v0.8.1）

- **现象**：单测暴露——计划自身计时在运行、另有跨设备并行事件时，"仅处置其他事件"却把计划自己的计时段停了。
- **根因**：两层。① `_settleAllRunning` 循环里调 `timer.stopCurrent()`，而它永远停 `running[0]`——当被排除的计时恰好排在首位时，后续迭代会误停别的事件（"循环变量"与"实际作用对象"不是同一个）。② 计划 store 的内存数组靠 onChange 延迟 ~30ms 刷新，调度动作紧跟写入发生时 `activePlan` 取到旧状态，空转返回。
- **修复**：`stopCurrent` 增加 `eventId` 参数按 id 精确结束；所有调度动作（start/_stopActive）入口先 `await this.load()` 回读库再决策，不再依赖订阅时序。
- **教训**：批量处置循环里不要依赖"默认对象"语义——每个动作必须显式指定目标；依赖事件订阅刷新的状态，在"写后立刻读"的调度链路里一律视为过期，先回读。

## 12. "CI E2E 偶发失败"的真凶：调试辅助硬编码 Windows 盘符路径（v0.9.0 后修正）

- **现象**：多轮发版 CI 的 E2E 时好时坏，本地 Windows 始终全过，一直按"Linux chromium 偶发"归档。
- **根因**：三个叠加。① 多个 spec 的调试辅助把产物写到硬编码 `E:/study/zi/MyTime/...`，Linux runner 上 `fs.writeFileSync` 直接 ENOENT，且这些写入在 step 的 catch/收尾里执行，一炸就把整条测试判死；② `e2e-summary.mjs` 的正则字面量里混进了真实换行（`replace(/↵/g)`），失败摘要脚本从未成功运行过——掩盖了 ① 的真实报错，逼出用浏览器爬 CI 日志的一次性 spec；③ 那个一次性 spec（read-ci-log）硬编码旧 run URL，本身又成了 CI 失败项。
- **修复**：新增 `web/e2e/helpers/debug.mjs` 统一产物路径（`path.resolve(process.cwd(),'..')` 跨平台）且所有调试写入吞错告警；删除一次性 spec；修正摘要脚本正则。
- **教训**：测试辅助代码也是被测代码的一部分，任何平台假设（盘符、绝对路径）都会在 CI 上兑现为失败；"调试逻辑的失败不应影响测试结果"要用 try/catch 明确保证，而不是默认它不会坏；把失败归因为"偶发"之前，先确保诊断管道本身（摘要脚本）是能跑通的。

## 13. SSH 全链路故障：Workbench 拒登、密钥签名失败、客户端静默降级（v0.9.0 当日）

- **现象**：Workbench 密码登录恒失败；本地密钥 ssh 报 `Permission denied (publickey,password)`；服务器 auth.log 只有 `Failed password`，没有 `Failed publickey`；非交互 ssh 偶发"挂起"。
- **根因（三层叠加，全部在客户端/入口侧，服务器配置无辜）**：① sshd 层密钥从未生效前 Workbench 密码登录撞上 `publickey` 单路认证（早期误判为密码错）；② 部署私钥带 passphrase 且无人知晓——`Server accepts key` 后需要口令解密私钥才能签名，BatchMode 下直接失败、交互下表现为"卡住"（在等口令输入）；③ Git Bash(MSYS) 的 chmod 在 Windows 盘上是空操作，私钥 0644 被 OpenSSH 拒载——`Offering public key` 能发出（用 .pub），签名这步静默失败坠落密码提示，制造了 `Failed password` 的误导性日志。
- **修复链**：控制台重置密码 → VNC 进入 → authorized_keys 补写公钥 → 本地重新生成**无口令**部署密钥（v3）→ icacls 收 ACL → 改用 Windows 自带 OpenSSH（按 ACL 校验，`cygpath -m` 转路径）；upload.sh 增加 SSH_CMD 解析优先用 Windows OpenSSH。
- **教训**：① `Server accepts key` 但 `Permission denied` = 签名环节出了问题（passphrase/私钥加载失败），不是服务器拒绝；② auth.log 只有 `Failed password` 而没有 `Failed publickey` 时，说明密钥根本没被出示——查客户端；③ 诊断输出被 `head` 截断会吃掉关键告警（`UNPROTECTED PRIVATE KEY FILE`），排障时保留完整 stderr；④ 探测脚本用 `BatchMode=yes` 只试密钥，会把"仅支持密码"误判成"仅支持密钥"——方法列表要结合 `-v` 全文读。

## 14. "移除密钥"二次翻车：git rm 换成了内容替换，跟踪从未断开（v0.10.0 当日）

- **现象**：v3 部署私钥（无口令）随功能提交进入公开仓库——而仓库早就为同类事故做过一次"移除"（ed71a52）并配置了 .gitignore。
- **根因**：ed71a52 的"移除"实际是**内容替换**（diff 显示 12 行改动而非文件删除）——文件从未离开 git 索引；而 **.gitignore 对已跟踪文件完全无效**，后续每次 `git add -A` 都会照常提交它。CRLF 警告列表是唯一暴露点，差点再次漏过。
- **修复**：`git rm --cached` 三件（私钥/公钥/deploy/config）断开跟踪并推送；密钥轮换 v4（git 历史里的 v3 视为已泄露：用历史中的 v3 私钥做最后一次救援登录，把 v4 公钥写入服务器、摘除 v3、销毁救援文件）；pre-commit 新增敏感文件跟踪闸门（`git ls-files` 全量 + 暂存区双检查，命中即阻断）。
- **教训**：①"移除敏感文件"提交后必须用 `git ls-files | grep <路径>` 验证为空才算完成——看 commit 消息/diff 摘要不可靠；② .gitignore 只防"未跟踪文件被加入"，已跟踪文件的排除要靠 `git rm --cached`，且要做进自动化检查而不是靠记忆；③ 已推送到公开仓库的私钥唯一正确的处置是**轮换**（服务端换锁），清史（filter-repo）只是锦上添花；④ 这类闸门该在第一次事故后就建——第二次事故的成本远高于闸门本身。
